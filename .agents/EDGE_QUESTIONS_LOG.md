## 2026-09-16 真实环境闭环测试、静默同步与双端 Edge 架构反思

### Q1: 为什么自动化测试全绿却未能暴露 `_dev_log` 双向同步脱节？如何破除“单向 Mock 的测试自欺欺人”？
- **原先假设/盲区**：
  此前测试用例主要覆盖本地→远端的 `submit_projection`、离散命令参数与 Mock 单元测试。研发中误以为“本地能推上去、远端返回成功”就等同于“完成了端到端开发闭环”，忽视了远端 AI 主动修改文件后的反向感知与自动收割。
- **事实与根因剖析**：
  1. **测试用例视角的单向局限**：所有的集成测试与用例均以“本地发起、远端响应”为闭环终点，缺乏“远端在异地异步生成改动 → 本地工作区如何被动/自动感知并合流”的逆向用例；
  2. **验证过程的伪通过**：在实际使用日本 VPS 测试时，执行的均为一次性的离散命令（`push`、单次 `run`），反向拉取通道处于完全静止状态；
  3. **白名单与触发通道脱节**：`_dev_log/` 虽已在 `.gitshadow` 白名单中，但若未显式执行 `--with-shadows` 拉取或未运行 `--watch` 监听循环，本地磁盘状态永远落后于远端。
- **架构决策与演进**：
  1. **防古德哈特反向测试门禁**：在测试套件中强制增加“双向逆向变更演练”（本地初始化 → 远端模拟 Agent 异步写入日志 → 本地执行拉取/自动合流 → 校验双端 SHA-256 一致）；
  2. **CAS 冲突三方验证纳入常态门禁**：不仅测试一致性，更要主动注入“本地远端并发冲突”，验证 CAS 冲突告警、三方比对与原子回滚能力。

### Q2: 摸索中涌现的隐性工程能力（Token 自愈、CAS 冲突等）如何 Skill 化？单体 `SKILL.md` 是否需要拆分？
- **原先假设/盲区**：
  最初把所有命令矩阵、运行哲学、环境避坑、底层协议全部堆叠在根目录单篇 `SKILL.md` 中。认为“一站式文档”最全，却导致文件膨胀至数百行，AI 上下文检索精准度下降，且缺少对具体复杂故障（如 CloudCLI 401 鉴权失效、CAS 并发冲突）的针对性可操作 SOP。
- **事实与根因剖析**：
  1. **能力发现与文档滞后**：在日本 VPS 实测中攻克了“从 `auth.db` 提取 `jwt_secret` 自动颁发 7 天 HS256 JWT”以及“CloudCLI 409 幂等重入”等关键能力，这些属于平台专有鉴权知识，散落在代码与调试日志中；
  2. **场景混杂挤占 Token**：开发者日常高频调用只需要轻量的命令速查和核心红线；而 CAS 冲突解决、Token 离线签名、服务进程自毁属于中低频的高阶故障处置，全塞在主入口会带来严重的上下文噪声。
- **架构决策与演进**：
  1. **实行 Skill 分层治理（Hub-and-Spoke 架构）**：
     - **主入口 `SKILL.md`（Hub）**：收敛为极简的交互导航、三态隔离哲学、核心命令速查与不可逾越红线；
     - **专项模块拆分至 `references/`（Spokes）**：
       - `references/CAS_CONFLICT_RESOLUTION.md`：CAS 冲突检测、三方比对与原子回滚 SOP；
       - `references/CLOUDCLI_DEEPLINK_AUTH.md`：自动提取密钥、颁发 7 天 HS256 JWT 与深链接入；
       - `references/CONTINUOUS_SILENT_SYNC.md`：持续自动同步、跨平台监听差异与租约自毁。
  2. **AI 按需精准展开**：日常执行读主文件，遭遇特定故障时再精准索引对应 reference。

### Q3: 现有“后台静默实现”在真实网络与跨平台下的有效性到底如何？它真的实现了“全静默”吗？
- **原先假设/盲区**：
  认为只要编写了 `LocalChangeWatcher` 和 `watch_shadow` 循环，就万事大吉声称“已支持持续静默同步”，忽视了跨平台兼容性、高频轮询开销以及离线脱机场景。
- **事实与根因剖析**：
  1. **从事实测缺失**：在前期测试中，全部是一次性手动命令，从未在真实公网环境下跑过长程持续监听；
  2. **Windows 平台监听退化**：`git_shadow/watcher.py` 底层只封装了 Linux 的 `inotify`，在 Windows 宿主下 `self.native` 为 `False`，退化为死循环 `sleep(0.3s)` 暴力重算哈希；
  3. **高频 SSH 轰炸远端**：`cli.py` 的轮询逻辑是每隔 2 秒无条件起一个全新的 `ssh` 进程拉取远端 Shadow，在跨国跨公网（本地到东京 VPS）下，进程反复创建开销极大，容易网络风暴或管道阻塞；
  4. **强依赖前台终端**：现有的 watch 逻辑被绑定在 CLI 前台主线程中，控制台窗口一关，同步彻底死亡。
- **架构决策与演进**：
  1. **禁止盲目高频起 SSH**：引入轻量级状态探针或长连接复用（SSH ControlMaster / 持久 Socket），严禁每 2 秒起一个完整 SSH 进程；
  2. **Windows 原生事件补齐**：后续接入跨平台文件监控，消除死循环暴力哈希；
  3. **现场真实压力测试**：在真实公网与 VPS 之间实测后台监控的延迟与系统资源消耗。

### Q4: 为什么当前架构出现了“远端做成了 Edge Agent，本地却退化为短命 CLI”的非对称变形？双端平权 Edge 架构如何收敛？
- **原先假设/盲区**：
  潜意识中依然沿用了传统的“本地是 Client，远端是 Server”思维，认为本地只需在想用的时候敲一下命令，远端常驻即可；导致本地一旦命令退出，整个双向静默通道立刻瘫痪。
- **事实与根因剖析**：
  1. **两端程序地位不平权**：远端开发了独立的无依赖单文件 `git-shadow-edge-agent.py`（RPC 执行器）和基于 Unix Domain Socket 的 `git-shadow-service-agent.py`（带 10 分钟租约自毁的常驻守护进程）；但本地却没有对应的守护进程，仅是一个由用户键盘触发的 CLI；
  2. **逆向推送无法实现**：远端改了代码，因为本地没有长驻接收端，远端无法主动将事件推给本地，只能被动等待本地下一次连上来“轮询”或“手动 pull”。
- **架构决策与演进**：
  1. **确立对称的双端 Edge 架构（Local Edge Daemon ⇄ Remote Edge Daemon）**：
     - **本地端**：提供本地后台守护能力（支持 `git shadow local service load/unload`，或未来作为桌面 Launcher 的后台引擎），直接监听本地内核文件事件；
     - **远端**：保持现有的 Linux 守护进程（带 10 分钟 Lease 超时自毁）；
     - **跨端通道**：两端 Edge 之间保持一条持久通信通道，任意一端有变更，毫秒级推送事件至对端；
  2. **彻底脱离终端窗口**：人类开发者只需在本地 IDE 保存文件，或远端 AI 在浏览器中生成代码，双端 Edge 在操作系统后台全自动静默完成 CAS 校验与同步，真正做到零命令、零黑框、零感知。
